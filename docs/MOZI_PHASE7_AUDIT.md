- 작성일: 2026-11-04
- 범위: 저장소 전체(백엔드, 프론트엔드, DB 마이그레이션, 문서, 테스트)

## 2. 정상 구현된 주요 기능

- **사용자별 데이터 분리:** 일기, 캐릭터, 만남, 사진, 리포트, 과거의 오늘을 모두 `user_id` 조건으로 조회한다. 다른 사용자의 일기를 조회, 수정, 삭제하거나 검색하면 404가 반환되는 테스트가 있다.
- **공유 페이지 개인정보 보호:** 공개 공유 응답에는 닉네임, 캐릭터 이름, 외형 부품만 들어 있다. 일기 원문, 제목, 날짜, 감정, 이메일, 사용자 ID는 없다 [재현].
- **XSS 방어:** 프론트에 `dangerouslySetInnerHTML`, `innerHTML`, `eval` 사용이 없다. 화면 출력은 React가 이스케이프한다.
- **로그 노출 없음:** 백엔드와 프론트 운영 코드에 일기 원문이나 키를 출력하는 로그가 없다.
- **입력 검증:**
  - 제목은 최대 100자, 본문은 길이 검증, 비밀번호는 8~64자다.
  - 닉네임은 허용 문자 패턴으로 검사한다.
  - 알림 시간은 정규식으로 검사한다.
  - 검색어는 최대 100자이고, 연도와 월 범위도 검사한다.
  - 미래 날짜 작성을 차단한다.
- **업로드 기본 방어:**
  - 형식은 PNG, JPEG, WebP만 허용하고, 크기 제한(아바타 2MB, 일기 사진 5MB)이 있다.
  - 파일 시작 바이트가 해당 이미지 형식과 맞는지 검사한다.
  - 저장 파일명은 UUID로 만들고, 경로 이탈을 막는다.
  - 업로드 파일은 공개 경로가 아닌 개인 폴더에 저장하고, 로그인한 본인만 내려받을 수 있다.
  - 응답에 `nosniff` 헤더가 붙는다.
- **중복 작성 방지:** 같은 날짜 일기는 DB 유일 제약과 IntegrityError 처리로 1개만 생긴다. 확정된 날짜에 다시 POST하면 기존 결과를 반환한다.
- **계정 권리:**
  - 데이터 내보내기(JSON)에 비밀번호 해시와 세션이 포함되지 않는다.
  - 탈퇴하려면 비밀번호를 다시 입력해야 한다.
  - 탈퇴하면 연관 데이터가 ORM cascade로 삭제되고, 업로드 파일도 지워진다. 이를 확인하는 테스트가 있다.
- **리포트:**
  - 날짜는 서울 기준이고, 주는 월요일부터 일요일까지다.
  - 짧은 달과 윤년을 보정한다.
  - 사용자가 수정한 분석 결과가 통계에 반영된다.
  - 각각 테스트가 있다.
- **마이그레이션 일관성:** 로컬 DB가 head 상태이고 모델과 스키마가 일치한다.

## 6. 수정 계획

모든 항목은 **DB 스키마를 바꾸지 않는 방법을 우선**한다. DB 변경이 필요해지면 따로 계획을 제시하고 승인을 받는다.

- **H1:** 본문이 Blob(File 포함)이면 호출하는 쪽에서 지정한 Content-Type을 유지한다. JSON 문자열 본문일 때만 `application/json`을 붙인다.
- **H2:** 코인은 그 일기에서 처음 캐릭터가 만들어질 때 한 번만 지급한다. `create_character_encounter`에 `award_coins` 인자를 추가한다. 최초 작성, `ai_failed` 이후 첫 데모 분석, 첫 재분석에서만 지급한다. 본문 수정, 감정 수정, 데모를 실제 분석으로 교체하는 경우에는 지급하지 않는다.
  - 스키마 변경은 필요 없다.
  - 이미 중복 지급된 코인은 회수하지 않는다. 회수가 필요하면 따로 정한다.
- **H3, H4:** 외부 의존성 없이 메모리에서 동작하는 고정 시간창 제한기를 만든다. 한도를 넘으면 429를 반환한다.
  - 로그인: 이메일과 IP 기준으로 15분에 10회
  - AI 호출(작성, 수정, 재분석, 회고): 사용자당 1시간에 20회. 이 숫자는 제안값이며 조정할 수 있다.
  - 서버가 여러 대이거나 재시작되면 제한이 초기화되는 한계가 있다. 이 점은 문서에 적는다.
- **M1:**
  - `Content-Length`를 먼저 확인하고, 본문은 조각 단위로 읽으면서 크기 상한을 넘으면 중단한다.
  - Pillow로 실제 이미지인지 디코딩해 확인한다.
  - 일기 사진은 다시 인코딩해서 EXIF를 제거한다. 이 단계는 원본 화질이 달라질 수 있으니 승인받은 뒤 진행한다.
- **M2:** 401 응답을 받으면 인증 상태를 anonymous로 바꾸고 로그인 화면으로 이동시킨다. 공개 공유 페이지는 제외한다.
- **M3:** 공개 응답에 `render_spec`을 넣되, 감정이 드러나는 키는 빼고 외형에 필요한 키만 넣는다. 먼저 `render_spec` 내용을 검토해서 넣을 키 목록을 확정한다.
- **M4:** `limit`과 `cursor`를 받는 선택 파라미터를 추가한다. 파라미터가 없으면 기존처럼 전체를 반환해서 호환성을 유지한다. 도감 화면에 "더 보기"를 넣는다.
- **M5:**
  - `APP_ENV=production`인데 Secure 쿠키가 꺼져 있으면 서버가 시작되지 않게 한다.
  - 기본 보안 헤더(X-Content-Type-Options, Referrer-Policy, frame-ancestors)를 추가한다.
  - 프로토타입 라우트는 개발 빌드에서만 등록한다.
- **M6:** 생성 결과 화면에서 `analyzing` 상태가 일정 시간 이상 계속되면 재시도와 데모 분석 버튼을 보여준다. 같은 일기를 동시에 수정하는 요청은 409로 응답한다.
- **M7:** 헤더 상태는 일기를 작성하거나 수정, 삭제했을 때만 다시 불러오고, 짧게 캐시한다.
- **Low:**
  - L3: 해당 테스트의 시간 제한을 늘리거나 무거운 부분을 나눈다.
  - L4: 문서를 현재 정책에 맞게 고친다.
  - L8: 서울 날짜를 쓴다.
  - L1: 로그인할 때 만료된 세션을 정리한다.
  - L2: 가입 시 이메일 중복 메시지 노출 방식을 검토한다. 정책을 결정해야 하는 부분이다.

## 7. 테스트 계획

| 대상 | 추가하거나 확인할 테스트 |
| --- | --- |
| H1 | `client.ts` 단위 테스트: File이나 Blob 본문이면 지정한 Content-Type이 유지되고, JSON 본문이면 `application/json`이 붙는지. 백엔드에서 실제 PNG 업로드가 200인 기존 테스트도 유지한다. |
| H2 | pytest: 작성 후 코인 150. 본문 수정과 감정 수정을 여러 번 해도 코인이 변하지 않음. `ai_failed` 후 데모 분석에서 1회 지급. 데모를 실제 분석으로 교체할 때 추가 지급 없음. 이번에 쓴 재현 시나리오를 회귀 테스트로 옮긴다. |
| H3, H4 | pytest: 로그인 10회 실패 뒤 429. 다른 계정이나 시간창이 지나면 다시 허용. AI 엔드포인트 한도를 넘으면 429이고 가짜 분석기 호출 수가 늘지 않음. |
| M1 | pytest: 시작 바이트만 맞춘 가짜 PNG는 422, 상한을 넘는 업로드는 413, EXIF가 있는 JPEG는 저장 뒤 EXIF가 없음. |
| M2 | Vitest: 보호된 화면에서 API가 401을 반환하면 로그인 화면으로 이동. 공유 페이지는 이동하지 않음. |
| M3 | pytest: 공개 응답에 원문, 날짜, 감정 키, 이메일, 사용자 ID가 없음(기존 검사 확장). 외형 필드는 있음. |
| M4 | pytest: limit과 cursor 페이지가 겹치거나 빠지지 않음. 파라미터가 없을 때 기존 응답과 같음. |

## 8. 승인이 필요한 결정

1. **수정 순서:** 위 우선순위대로 진행할지 정해야 한다. 그 전에 현재 변경을 커밋할지(L7)도 정해야 한다.
2. **H2 이미 지급된 코인:** 그대로 둘지, 별도 스크립트로 정리할지 정해야 한다. 정리하려면 DB 데이터를 수정해야 하므로 별도 승인이 필요하다.
3. **H3 AI 호출 한도:** 사용자당 1시간 20회로 할지, 다른 숫자로 할지 정해야 한다.
4. **M1 사진 재인코딩:** 일기 사진을 다시 인코딩하면 EXIF가 지워지지만 화질이 조금 달라질 수 있다. 진행할지 정해야 한다.
5. **E2E 도구:** Playwright 같은 새 개발 의존성을 추가할지 정해야 한다.
