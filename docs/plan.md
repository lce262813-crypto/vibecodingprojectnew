# MOZI 5일 MVP 개발 계획

## 1. 문서 목적

이 문서는 [MVP 기획서](./mvp.md)와 [기능 동작 명세서](./spec.md)를 실제 구현 작업으로 나눈 실행 계획이다.

목표는 5일 안에 다음 전체 흐름을 시연하는 것이다.

```text
회원가입
→ 로그인
→ 오늘의 일기 작성
→ AI 또는 데모 감정 분석
→ 캐릭터 생성 또는 재등장
→ 도감 자동 저장
→ 감정 방 입주와 움직임
→ 캐릭터 공유
```

공개 배포는 아직 확정하지 않는다. 우선 로컬 환경에서 전체 흐름이 안정적으로 동작하게 만든다.

## 2. 작업 원칙

1. 한 번에 한 Phase만 진행한다.
2. 각 Phase의 완료 조건을 확인한 뒤 다음 Phase로 넘어간다.
3. 화면만 성공한 것처럼 보이는 가짜 저장 기능을 만들지 않는다.
4. 테스트용 예시 데이터와 실제 저장 데이터를 분명히 구분한다.
5. 사용자 A의 데이터가 사용자 B에게 노출되지 않는지 매 단계 확인한다.
6. 비밀번호, API 키와 실제 `.env` 값을 코드, 문서, Git과 답변에 넣지 않는다.
7. 기존에 완료한 기능을 다음 Phase에서 불필요하게 다시 작성하지 않는다.
8. 일정이 밀리면 새 기능을 추가하지 않고 기존 MVP 기능의 표현을 단순화한다.

## Phase 0. 개발 기준과 환경 확인

**상태: 완료 (2026-11-02)**

### 목표

코드를 만들기 전에 문서와 실행 환경의 충돌을 제거한다.

### 작업

1. `mvp.md`, `spec.md`, `plan.md`의 기능 범위가 일치하는지 확인한다.
2. Node.js, npm, Python과 Git 사용 가능 여부를 확인한다.
3. React, Vite, Tailwind CSS, FastAPI, SQLAlchemy와 PostgreSQL의 호환 가능한 안정 버전을 정한다.
4. Supabase 프로젝트와 `DATABASE_URL` 준비 여부를 확인한다.
5. OpenAI API 키는 사용자가 로컬 `.env`에 직접 입력하도록 준비한다.
6. 프론트엔드와 백엔드의 로컬 주소를 정한다.
7. 백엔드 테스트, 프론트엔드 테스트와 빌드 명령을 정한다.
8. 공개 배포는 보류 상태임을 유지한다.

### 예상 변경 파일

- `docs/setup.md`
- `.env.example`
- `.gitignore`

### 확인 방법

- 필요한 도구의 버전을 터미널에서 확인한다.
- `.env`가 Git 추적 대상에서 제외되는지 확인한다.
- `.env.example`에 비밀값이 없는지 확인한다.
- 로컬 포트가 다른 프로그램과 충돌하지 않는지 확인한다.

### 완료 조건

- 기술 선택과 실행 명령이 문서화되어야 한다.
- 실제 비밀값이 저장소에 없어야 한다.

## Phase 2. 데이터베이스와 회원 기능

**상태: 로컬 구현 완료, Supabase PostgreSQL 검증 대기 (2026-11-02)**

### 목표

사용자가 가입하고 로그인한 뒤 자신의 보호된 감정 방 화면에 들어가게 한다.

### 작업

1. SQLAlchemy 데이터베이스 연결과 마이그레이션 도구를 설정한다.
2. 사용자와 세션 모델을 만든다.
3. 이메일과 닉네임 유일 제약을 둔다.
4. 안전한 비밀번호 해시와 검증 기능을 만든다.
5. 회원가입 API와 입력 검증을 만든다.
6. 로그인, 현재 사용자 조회와 로그아웃 API를 만든다.
7. HTTP-only 세션 쿠키를 설정한다.
8. 랜딩, 회원가입, 로그인과 감정 방 빈 화면을 만든다.
9. 프론트엔드 보호 라우트와 로그인 상태 복원을 연결한다.
10. 닉네임 변경은 계정 설정의 최소 화면까지 연결한다.

### 예상 변경 파일

- `backend/app/db/`
- `backend/app/models/user.py`
- `backend/app/models/session.py`
- `backend/app/schemas/auth.py`
- `backend/app/services/auth.py`
- `backend/app/api/auth.py`
- `backend/tests/test_auth.py`
- `frontend/src/auth/`
- `frontend/src/settings/`
- `frontend/src/room/RoomPage.tsx`
- `frontend/src/api/client.ts`

### 확인 방법

- 이메일, 비밀번호, 닉네임으로 가입한다.
- 같은 이메일과 닉네임의 중복 가입을 막는다.
- 비밀번호 경계값 8자와 64자를 확인한다.
- 가입한 계정으로 로그인한다.
- 로그인하지 않은 사용자가 보호된 화면에 접근하지 못한다.
- 새로고침 뒤에도 유효한 세션이 복원된다.
- 로그아웃 뒤 보호된 화면을 볼 수 없다.

### 완료 조건

- 회원가입부터 로그인, 보호된 감정 방 진입까지 실제 데이터로 동작해야 한다.
- 사용자 A와 B의 인증 상태가 섞이지 않아야 한다.

## Phase 4. 실제 AI 분석과 데모 모드

**상태: 구현 완료, 실제 OpenAI 호출 검증 대기 (2026-11-02)**

### 목표

일기를 16개 기본 감정과 세부 상태로 분석하고 검증된 결과를 저장한다.

### 작업

1. 감정 분석 응답 스키마를 코드로 정의한다.
2. 기본 감정 16개와 세부 상태 20개 키를 상수로 만든다.
3. OpenAI 호출을 백엔드 서비스에만 연결한다.
4. 구조화된 JSON 응답을 스키마로 검증한다.
5. 화면용 상위 감정 최대 3개와 합계 100% 비율을 계산한다.
6. 감정 분석 모델과 마이그레이션을 만든다.
7. AI 실패 상태, 다시 시도 API와 화면을 만든다.
8. 같은 스키마를 반환하는 규칙 기반 데모 분석기를 만든다.
9. `데모 분석으로 계속하기` 선택과 표시를 연결한다.
10. 일기 원문과 API 키가 로그에 남지 않게 확인한다.

### 예상 변경 파일

- `backend/app/models/emotion_analysis.py`
- `backend/app/schemas/emotions.py`
- `backend/app/services/openai_analysis.py`
- `backend/app/services/demo_analysis.py`
- `backend/app/services/emotion_display.py`
- `backend/app/api/diary.py`
- `backend/tests/test_emotion_analysis.py`
- `frontend/src/diary/AnalysisFailure.tsx`
- `.env.example`

### 확인 방법

- 가짜 OpenAI 응답으로 정상 스키마를 저장한다.
- 16개 점수 누락, 범위 밖 점수와 잘못된 감정 키를 거부한다.
- 표시 감정이 1~3개이고 비율 합계가 100인지 확인한다.
- AI 오류 후 다시 시도한다.
- AI 오류 후 데모 분석을 선택한다.
- 데모 사용 여부가 화면과 DB에 남는다.
- API 키와 일기 원문이 오류 응답과 로그에 없는지 확인한다.

### 완료 조건

- 실제 분석과 데모 분석이 같은 내부 계약으로 저장되어야 한다.
- 잘못된 AI 응답으로 캐릭터 생성 단계가 시작되지 않아야 한다.

## Phase 5. 캐릭터 파츠와 결정적 생성 엔진

**상태: 완료 (2026-11-02)**

### 목표

분석 결과로 재현 가능한 픽셀 캐릭터를 생성하고 비슷한 감정에서 같은 캐릭터를 재사용한다.

### 작업

1. 공통 가상 캔버스와 SVG 파츠 규칙을 확정한다.
2. 최소 몸통 4개와 핵심 얼굴 파츠를 만든다.
3. 16개 감정의 기본 표정 레시피를 만든다.
4. 강도 5단계가 표정과 효과를 바꾸게 한다.
5. 세부 상태 20개의 추가 파츠 또는 효과 매핑을 만든다.
6. 키워드를 10개 장식 분류로 변환한다.
7. 감정 지문과 사용자별 결정적 랜덤 시드를 구현한다.
8. 캐릭터, 만남 모델과 마이그레이션을 만든다.
9. 같은 지문이면 기존 캐릭터, 다른 지문이면 새 캐릭터를 선택한다.
10. 파츠 ID, 색상, 시드와 알고리즘 버전을 저장한다.
11. 기본 캐릭터 이름을 생성한다.
12. 결과 공개 화면에 SVG 합성과 기본 모션을 표시한다.

### 확인 방법

- 같은 사용자와 같은 감정 지문에서 같은 캐릭터 ID와 외형을 얻는다.
- 같은 사용자와 다른 지문에서 다른 캐릭터가 생성된다.
- 다른 사용자는 같은 지문에서도 사용자별 시드가 다르다.
- 새로고침과 재로그인 뒤 외형이 바뀌지 않는다.
- 키워드 장식이 달라도 기본 캐릭터는 유지된다.
- 분석부터 캐릭터·만남 저장이 하나의 작업으로 완료된다.

### 완료 조건

- 일기 작성부터 캐릭터 결과까지 실제 데이터로 연결되어야 한다.
- 결과 화면에 도착하기 전에 캐릭터와 만남이 저장되어 있어야 한다.

## 6. 일정이 밀릴 때의 단순화 순서

기능을 삭제하기 전에 표현 복잡도를 다음 순서로 줄인다.

1. 몸통과 돌연변이 파츠 수를 최소 목표까지만 만든다.
2. 세부 상태 전용 파츠를 공통 효과 파츠로 재사용한다.
3. 감정 방의 이동 경로를 좌우 중심으로 단순화한다.
4. 행동 유형별 모션 수를 하나씩만 유지한다.

- 하루 한 번 일기
- 실제 AI와 데모 분석
- 캐릭터 생성 또는 재등장

- 감정 방 기본 상태는 벽, 바닥, 창문만 있는 빈 방이다.
- 일기로 캐릭터를 만나면 100코인, 새 캐릭터면 50코인을 더 받는다. 기존 사용자는 마이그레이션 `0007`에서 같은 기준으로 코인을 소급 지급했다.
- 상점(`/shop`)은 벽 장식·창문·가구·소품·조명·바닥 5개 카테고리, 24종 가구를 판다. 가구마다 정해진 자리(slot)가 있고 같은 자리에는 하나만 놓인다. 다른 가구를 놓으면 기존 가구는 창고로 간다.
- 창문은 그날의 실제 날씨(Open-Meteo, 키 불필요)를 보여준다. 맑음·흐림·비·눈·뇌우 × 새벽·낮·노을·밤이며, 시간대는 그날의 일출·일몰 시각(일출 ±40분은 새벽, 일몰 50분 전~30분 후는 노을)으로 1분마다 다시 정한다. 새벽·노을·밤에는 방 전체에 은은한 빛 색을 입히고 캐릭터는 그대로 밝게 보인다. 브라우저 위치를 쓰고 권한이 없으면 서울 기준이다. 날씨 이미지는 `scripts/generate_window_weather.py`가 만든다.
- 가구 이미지는 `scripts/generate_room_background.py`가 방과 같은 192×108 캔버스의 투명 레이어로 만든다.
